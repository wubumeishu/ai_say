# 01 · 背景 · 现状 · 目标 · 总体架构

> Ai SAY 项目计划书 · 第 1 章
> 本文是后续 02 数据模型 / 03 引流与私域 / 04 路线图 的基础章节。

---

## 1. 背景与现状问题

Ai SAY 当前是一个基于 BitBrowser + DevTools(CDP) 的消息监控与翻译工具：
浏览器里挂着若干平台账号窗口（如「自用出会」平台的多条私信会话），
server 端通过 CDP 连接抓页面、翻译消息、存画像。
随着账号窗口和客户数量的增加，现有做法暴露出三个结构性问题：

### 1.1 按窗口逐个处理，无法横向扩展
- 每个浏览器窗口（windowId）被当作一个独立实体，监控、抓取、翻译逻辑都绑死在具体窗口上：
  `SessionPool` 以 `browserId` 为 key，`normalizeAccountKey(windowId, platform, accountLabel)` 以三元组拼 key。
- 新增窗口、平台或账号时，都要逐个接入、逐个调参；同一客户在不同窗口/平台出现时，被当成互不相干的"陌生人"。
- 窗口崩溃、CDP 断连后只能逐窗口恢复，没有统一的消息来源抽象。

### 1.2 账号与客户的画像靠人工记忆
- 客户信息目前散落在各平台的界面里（如 `contact.candidates` 里一堆 "♂爽快！さん 46歳 埼玉県"），
  或者靠操作者自己记住"这个客户上次聊了什么、要过什么"。
- 没有从聊天文本中自动抽取 年龄/地区/职业/意向/历史偏好 的能力，
  画像要么缺失、要么靠人工补录，重复工作多且不一致。

### 1.3 数据三元组冗余（platform / windowId / 客户）
- `data/` 下三个 JSON（`account-profiles.json`、`conversations.json`、`contacts.json`）
  全部以 `platform + windowId + label` 三元组为主键：
```
key = "自用出会/2315e879dd6642559bdc11a07bb1fc43/AA_test"
```
- 同一个真实客户在两个窗口里会生成两条记录；客户换了登录方式/换了昵称就变成"新客户"。
- 平台私信与 LINE 里的同一个客户完全没有关联，无法打通成统一客户视图。

> 结论：现有系统是"**窗口视角**"的监控工具；下一步需要变成"**客户视角**"的统一运营系统。

## 2. 目标

| # | 目标 | 说明 |
|---|------|------|
| G1 | **账号无关的统一消息处理** | 消息进入系统后不再关心"来自哪个窗口"，按 平台+账号+客户 归一化，窗口只是采集通道 |
| G2 | **自动画像与去重** | 从聊天文本自动抽取 年龄/地区/职业/意向/历史偏好，带置信度；同一客户多次出现自动归并，不产生重复档案 |
| G3 | **跨平台客户打通** | 平台私信 ↔ LINE 客户按稳定身份锚点合并成 unified profile，一处可见全生命周期 |
| G4 | **自动引流** | 识别可引流量客户（回复快、留联系方式意愿、高意向关键词），自动生成合规话术把客户引导到 LINE |
| G5 | **LINE 私域** | 通过 LINE 官方 API 建立私域客户池：加好友、双向消息、客户标签群，承接引流来的客户 |
| G6 | **卡片式统一控制台** | 所有客户/会话/引流事件以卡片形式聚合在 web 控制台，替代"逐窗口看页面"的操作方式 |

验收口径（细粒度指标见 04-roadmap.md）：
- 自动处理覆盖率：无需人工逐窗口介入的消息占比；
- 去重准确率：同一客户被正确归并而非新建档案的比例；
- 引流成功率 / LINE 转化率：意向客户中被成功引导至 LINE 的比例。

## 3. 统一身份模型

### 3.1 稳定身份锚点（替代手工 windowId+platform 三元组）

三元组的问题是"绑定采集通道"而非"绑定客户"。新模型用**客户侧稳定信号**做主锚点，
三元组降级为"观测源"（observation source），不再是身份本身：

| 锚点 | 来源 | 稳定性 | 用途 |
|------|------|--------|------|
| LINE 账号 ID（`LINE_USER_ID` / email） | 客户主动留 LINE / LINE API 回传 | 高 | 最强锚点，跨平台合并的"金标准" |
| 邮箱 | 聊天留资 / 平台资料页 | 中 | 次强锚点 |
| 设备指纹（UA + 浏览器窗口特征 hash） | CDP 采集 | 低-中 | 仅用于"同渠道去重"，不作为跨平台合并依据 |
| 平台内 ID（profileUrl 里的用户 id） | 平台资料页 | 中 | 平台内唯一键 |

规则：
1. 客户实体（Contact）的 `identityAnchors` 数组保存所有已知的锚点；
2. 合并判定：**任一强锚点（LINE/邮箱）相同 ⇒ 同一客户，直接合并**；
3. 只有弱锚点相同（同设备指纹、同昵称同地区）⇒ 标记 `likelySame`，进待确认队列，不自动合并；
4. 锚点可多对一：一个客户可以同时拥有 LINE + 邮箱 + 平台内 ID，全部挂到同一个 Contact。

### 3.2 账号人设 vs 客户画像（严格分离）

身份模型里，**账号侧**与**客户侧**是两个互不污染的方向，各走各的 schema：

| 概念 | 实体 | 描述什么 | 举例 |
|------|------|----------|------|
| **账号人设（AccountPersona）** | `AccountPersona` | 账号本体：人设设定、语气、背景故事、目标人群、禁忌词 | 账号 #1 设定为「东京自由摄影师，30 代，对运动话题感兴趣，禁忌低俗话题」 |
| **客户画像（CustomerProfile）** | `ContactProfile` | 客户是谁、要什么，独立于任何账号 | 客户 A：38 岁埼玉、找同城、明确拒绝成人向 |

规则：
1. 账号人设挂在 **Account** 实体上，不挂 Client 身上；同一账号在不同平台的窗口共用一份人设；
2. 客户画像挂在 **Contact** 实体上，不感知账号人设，字段里没有任何「按哪个账号聊天的视角」；
3. 两者**禁止直接引用对方的字段**：账号人设不存客户 A 的画像，客户 A 的画像不存账号 #1 的人设；
4. 合并客户（§3.4）时，**只合并客户画像与消息历史**，与账号人设无关；账号归并（§3.3）时只合并账号资料，与客户画像无关。

> 设计意图：让"谁在说"（账号人设）与"对谁说"（客户画像）解耦，避免人设漂移污染客户档案，也避免客户特征被误认为是账号本身的属性。

### 3.3 账号归并算法（平台账号侧）

- 平台账号（Account 实体）同样支持归并：同一人在不同平台用相似昵称/邮箱时，
  人工或规则（邮箱相同）可把两个 Account 标记为 `samePerson`，画像互相补充而不覆盖；
- 归并采用**不删除原记录**的方式：保留 `mergedInto` 指针，历史消息仍挂在原账号下，
  聚合视图按归并后的根账号展示。

### 3.4 客户去重合并策略

- 去重发生在**写入时**（upsert 阶段）：先算锚点集合 → 命中强锚点直接并入；
  命中弱锚点入候选队列；都没命中才新建；
- 字段冲突解决：
  - 画像字段（年龄/地区等）取**置信度更高**的取值，两者都不高则保留旧值并记 `conflicts`；
  - 消息历史**永不覆盖**，只追加；
  - 时间戳取 `max(updatedAt)`；
- 每个合并动作写一条 `mergeEvent`（谁并了谁、依据哪个锚点、何时），可审计可回滚。

详细 schema 与迁移映射见 02-datamodel.md。

### 3.5 画像建立顺序（资料页优先）

**两步法，固定顺序不可颠倒**：
1. **第一步：资料页建立基础画像**。账号首次接触某客户时，优先抓取其平台资料页（`profileScan` / `profileInspector` 已验证的 17098 分组：基本/详细/兴趣/成人交友），产出该客户的**基础画像**（昵称、年龄、地区、兴趣、交友状态等页面可观测字段）。此时客户尚未开聊，资料页是唯一可靠来源；
2. **第二步：聊天补充细节**。基础画像入库后，聊天消息流才进入 ③画像抽取器，**只负责补充资料页未覆盖的字段**（意图、历史偏好、回复习惯等）；客户自述与页面字段冲突时按 §3.4 的置信度规则取高值。

顺序约束的意义：资料页字段置信度天然高于聊天自述（平台已校验的结构化数据），先入页字段再进聊天细节，避免"聊天口误覆盖页面真值"的降级问题；与 02 章 §2 抽取器管线、04 章 M1 验收口径（资料页优先）对齐。

### 3.6 统一规则 GovernanceRule（全局生效）

- `GovernanceRule` 是一等实体，字段：`ruleType`（合规红线 / 话术边界 / 频控 / 品牌口径）、`scope`（global / platform / account / channel）、`priority`、`status`（active / draft / deprecated）；
- 语义：**无论 1 个账号还是 N 个账号，合规红线、话术边界、频控、品牌口径完全一致**，不随账号人设变化、不随客户画像变化；
- 下发契约：④推荐/引流引擎与 ⑤LINE 适配器在生成任何外发内容前，必须查询当前生效的 `GovernanceRule`（按 scope 叠加：global ⊃ platform ⊃ account，高优先级覆盖低）；合规类规则未命中默认拒绝，非合规类未命中默认放行；
- 规则增改统一走 ⑥控制台（M5），每次变更写审计日志，可一键回滚到上一版本；
- 规则与账号人设的边界：**人设管「怎么说」（风格/语气），GovernanceRule 管「能不能说、能说什么」（边界/红线）**，两者正交叠加，冲突时 GovernanceRule 胜出。

完整字段与下发契约见 02-datamodel.md §1.2 / §6。

## 4. 总体架构

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  采集层（现有，继续演进）                                                      │
│  BitBrowser 窗口 ──CDP──▶ DevToolsClient ──▶ SessionPool ──▶ MessageMonitor │
└──────────────────────────────────┬──────────────────────────────────────────┘
                                   │ 平台原生事件（新消息/新会话）
                                   ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  ① 消息总线 Message Bus                                                    │
│     统一事件模型：{ source: {platform, account, windowId}, contactAnchors,  │
│                   text, time, raw }                                          │
│     窗口只是 source 字段；下游不关心窗口                                      │
└──────────────────────────────────┬──────────────────────────────────────────┘
                                   ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  ② 会话聚合器 Conversation Aggregator                                        │
│     按 (平台, 账号, 客户ID) 归一化会话；跨窗口的同客户会话合并为一条时间线      │
└──────────────────────────────────┬──────────────────────────────────────────┘
                                   ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  ③ 画像抽取器 Profile Extractor（自动画像）                                   │
│     从消息文本抽取 年龄/地区/职业/意向/偏好，带置信度 → upsert 到 Contact       │
│     （身份锚点合并 & 去重，见 §3）                                            │
└───────────┬──────────────────────────────────┬─────────────────────────────┘
            ▼                                  ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  ④ 推荐 / 引流引擎 Recommendation & Lead Engine                              │
│     意向识别（回复速度/关键词/留资）→ 自动话术生成 → 引流事件 LeadEvent          │
│     （合规、频控、A/B，详见 03-acquisition.md）                              │
└──────────────────────────────────┬──────────────────────────────────────────┘
                                   ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  ⑤ LINE 适配器 LINE Adapter                                                  │
│     LINE Messaging API / LINE Login：加好友、双向消息、标签同步回 ③/④         │
└──────────────────────────────────┬──────────────────────────────────────────┘
                                   ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  ⑥ 统一后台 Unified Console（卡片式）                                        │
│     客户卡片（unified profile + 全渠道时间线）/ 会话卡片 / 引流事件卡片        │
│     人工确认队列（likelySame 待归并、话术待审）                                │
└─────────────────────────────────────────────────────────────────────────────┘
```

数据流要点：
- **单一写入路径**：所有来源（平台消息、LINE 回调、人工补录）都先落到 ①消息总线，
  再由 ②③ 归一化入库，避免现在的"每个窗口各自写 JSON 文件"；
- **③是去重/归并的闸门**：任何新接触信息都必须先过身份锚点判定，保证 Contact 不膨胀；
- **⑤双向**：LINE 侧回传的消息也进 ①，使 unified profile 同时被平台侧与 LINE 侧喂养；
- **⑥只读聚合**：控制台读的是聚合后的实体，不再读原始三元组文件。

## 5. 与现有 server/ 的演进关系

| 现有模块 | 当前职责 | 演进方向 | 处置 |
|----------|----------|----------|------|
| `devtools.js` | CDP WebSocket 客户端：attach 目标、evaluate、事件订阅 | 不变，作为采集层底座 | 保留 |
| `sessionPool.js` | 每窗口一条长连接 CDP，健康检查与断连恢复 | 保留"窗口级连接管理"；**向上暴露统一事件**，把"窗口身份"下沉为事件的 `source` 字段 | 保留 + 加事件出口 |
| `store.js` | 三元组 key 的 JSON 文件存储（profiles/conversations/contacts） | **重构为新实体模型**（Account/Contact/Conversation/LeadEvent/LineBind）；旧三元组文件作为**迁移源**一次性映射，读路径兼容期保留 `legacyKey` 字段 | 重写存储层，接口保留 upsert/list 形状 |
| `messageMonitor.js` / `messagePageScanner.js` | 轮询/抓消息页、翻译 | 改为向 ①消息总线**发布**标准化事件，而非直接写 store | 改造为 bus publisher |
| `profileScan.js` / `profileInspector.js` | 抓资料页、生成画像草稿 | 输出接入 ③画像抽取器，作为"平台资料页锚点来源"之一 | 保留为抽取器上游 |
| `aiService.js` / `translator.js` | 翻译与 AI 推荐 | 成为 ③④ 的模型能力层（抽取、话术生成共用一套 AI 调用） | 下沉为公共能力层 |
| `bitbrowser.js` / `devtoolsTargets.js` | BitBrowser 管理、CDP target 选择 | 不变 | 保留 |
| `queueScanner.js` / `index.js` / `app.js` | 队列扫描、HTTP 装配 | 控制台 API 面向新实体重写；旧三元组 API 保留一个版本的兼容路由 | 渐进重写 |

演进原则：
1. **采集层（devtools/sessionPool/bitbrowser）不动**，业务逻辑下沉到新实体层，
   避免把窗口身份泄漏到业务语义里；
2. **store 是唯一大重构**，但保持 `upsert/list` 的 API 形状，
   让 ①~⑥ 可以先按新实体开发，旧文件经迁移脚本一次性搬入；
3. 每一步都保持旧三元组文件**可读**（`legacyKey`），迁移完成前新旧并存；
4. 具体模块拆分与里程碑验收见 04-roadmap.md（M0 数据模型重构 → … → M5 控制台）。
